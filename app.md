# Tellius Modding app

The app is a Windows Python/Tkinter desktop application for modifying *Fire Emblem: Path of Radiance* (GameCube) and *Fire Emblem: Radiant Dawn* (Wii). It organizes work into projects, extracts a source disc, exposes supported game data through editors and viewers, and rebuilds a playable disc image.

The application source is under `App/`.

## Commands

Run these commands from `App/`:

```bash
python main.py
python -m unittest discover -s tests -v
```

## Architecture

The app has four main layers:

1. **Project and game layer** — `fe_modding/project.py`, `games.py`, `config.py` and `patch.py` define projects, supported games, recent projects and settings, the extract/build lifecycle, and `.tpatch` mod patches. `patcher.py` (entry `patcher_main.py`) is Tellius Patcher, the Apply-patch window on its own for players; `release/build_windows.py` builds it as the one-file `TelliusPatcher.exe`. `hub.py` / `hub_creation.py` make a campaign hub: Chapters › Create hub copies a template chapter with the avatar alone, and the hub chapter's Build tab gets a Hub tool (`gui/hub_tool.py`) that places the chapter links on the map, kept in `hub_draft.json` until Install hub (see [App/docs/HUB_SETUP.md](App/docs/HUB_SETUP.md)).
2. **Desktop workspace** — `fe_modding/gui/` contains the launcher, the workspace shell (top-bar sections, Disc & Patch button, breadcrumbs, back/forward, Ctrl+K search, status bar), the pages (`gui/pages/`: Home, Chapters, a page per chapter, Characters, a page per character, Game Data (a tile per section: Classes … Supports, Flags, AI), Assets (with Map Objects), Tools (Battle Simulator, Saves, Game Code), Disc & Patch), the Settings and Apply-patch dialogs, the editors and viewers they embed, the theme (`gui/theme.py`, Sun Valley light/dark) and the in-session change log. `fe_modding/project_index.py` joins the formats (characters, deployments, messages, scripts) for the chapter and character pages. `fe_modding/script_sources.py` loads and saves event scripts as source for the Script tab and the Flags tab.
3. **Game-data layer** — `fe_modding/formats/` reads and, where supported, writes the binary, image, audio, video, script, map, and model formats used by the games.
   Assets › Animation Data uses the shared `gui/animation_data_viewer.py` surface: PoR records come from `anim_registry.py`, while `fe10_anim.py` structurally decodes RD's 390 headers, 245 model records, 48 motions and nine weapon mappings, including relocated strings and header/model links; RD numbered animation variants are editable in place.
   `fe_modding/battle_sim/` is the battle simulator's rules engine (Path of Radiance forecast, strike order, skills, seeded or fixed rolls; units levelled and promoted with the fixed growth mode in `units.py`), with no Tk code, plus the engine's battle staging (`staging.py`: `zdbx/param.dbx` and `_prm.dbx` values; `timeline.py`: each strike tick by tick as `main.dol` stages it; `camera.py`: the `xcam/` scripts, tweens, mirroring and shake) and the battle-asset lookup; `formats/battle_terrain.py` places a `zbg/` backdrop. Tools › Battle Simulator (`gui/battle_simulator.py`) drives it; **Render fight** opens `gui/battle_window.py`, which plays the fight in real time with the battle models (`gui/battle_stage.py`, also used by the playthrough's battle window). Its body, `BattlePlayer`, is also embedded by Assets › Battle Cameras to preview a camera script (as edited) with two default units in a chosen scenery.
   `fe_modding/playthrough/` plays a chapter without the game, also without Tk code. It covers movement, the player's actions (Attack, Staff, Shove, Talk, Visit and the other tile actions, Canto) and fights through `battle_sim`. A `.cmb` interpreter (`event_vm.py`, natives in `natives.py`) runs the event triggers, a `cp_data.bin` interpreter (`ai_vm.py`) runs the enemy phase in turn order, and messages show one page at a time. Every step is one script instruction, message page or AI entry. The whole state is plain data, so `simulation.py` keeps a snapshot per step for going back, going forward and branching. The Build tab's **Play...** button opens `gui/playthrough_window.py`, with optional battle animations (`gui/playthrough_battle.py`). Some of it is approximate:
   - autolevelled stats use average growths;
   - the AI picks targets and tiles with its own score built from the MTYPE weights;
   - natives and AI ops that aren't modelled are logged and return 0;
   - fog is a view only (`playthrough/fog.py`: tiles within the class's vision of a player unit; no torches, roofs or line of sight) and does not limit the AI; there is no base screen, and the preparations are reduced to choosing which units are placed (when the opening deploys nobody);
   - choice dialogs take the first entry unless the window's **Choices...** plan names another (`GameState.choice_plan`).
4. **External-tool layer** — `fe_modding/tools.py` invokes WIT and FFmpeg from developer-provided `tools/` binaries or the per-user tool cache for disc operations and general video decoding. `fe_modding/emulator.py` finds and starts Dolphin on a built image; a chapter page's **Play in Dolphin...** button (also **Play > Play chapter in Dolphin...**, F5, which asks for the chapter when no chapter page is open; Ctrl+F5 builds and plays the disc) skips the build: it copies `extracted/sys` into `build/dolphin_run/` with a `main.dol` that boots straight into that chapter on the chosen difficulty with a fresh army (`game_code/chapter_jump.py` / `chapter_jump_fe10.py`), links `files` there as a directory junction to `extracted/files`, and has Dolphin boot that folder's `sys/main.dol`. Radiant Dawn run trees also copy the Wii partition metadata and `disc/` directory required by Dolphin's DirectoryBlob loader. The project's own `main.dol` is never patched for it.

Editors operate directly on files in a project's `extracted/` directory. Building a project packages the current contents of that directory; there is no separate apply or staging step.

The two games share the architecture, but game-specific disc formats and build outputs are centralized in `fe_modding/games.py`. Path of Radiance builds to CISO and Radiant Dawn builds to WBFS. Disc images can also be `.rvz`: WIT cannot read that format, so `tools.extract_disc` converts it to a temporary ISO with `DolphinTool` (found next to the configured `Dolphin.exe`) and extracts that. A Wii disc is extracted from its DATA partition and the result must hold `sys/`, `files/`, `disc/`, `ticket.bin`, `tmd.bin` and `cert.bin`. The Disc & Patch page exposes the complete workflow for both games: selecting and extracting the source, rebuilding and launching it, creating and applying `.tpatch` files, editing mod metadata, and exporting decoded data for version control. Radiant Dawn's export writes semantic FE10Data and FE10Growth JSON, lossless readable message notation, and decompiled `.fe10s` scripts.

Everything that differs per game goes through a `GameProfile` (`fe_modding/game_profile.py`, reached as `project.profile` or `games.profile(game)`) instead of `if game ==` checks. It holds the logical-to-physical file map (`game_data` is `FE8Data.bin` on Path of Radiance and the LZ10-compressed `FE10Data.cms` on Radiant Dawn; likewise `anim_data`, `battle_data`, `ai_data`...), the chapter id scheme and file templates (`C05.cmb` / `C0101.cmb`, `dispos.cmp` / `dispos_<n|h|c>.bin`, `shop/` / `Shop/`), the difficulty letters, and the set of **features** that have a decoder for the game. `project.read_logical(name)` / `write_logical(name, data)` read and write a logical file with the LZ10 layer handled. A screen whose feature the profile does not list shows "... is not available for Radiant Dawn yet" (`profile.unavailable(feature)`) instead of reading a layout it does not understand; switching a feature on in the Radiant Dawn profile is how a new decoder is released. Features also name data only one game has (`ending_art` and `tutorials`/`staff_credits` for Path of Radiance until Radiant Dawn's formats are decoded, `battle_skies` for Radiant Dawn): an Assets tool tied to one (`ASSET_APPLIES` in `gui/pages/assets.py`) is left out of the hub, the search and its route on the other game rather than shown as unavailable. Capability features that still lack a Radiant Dawn decoder gate their controls the same way: `playthrough` (the Build tab's **Play...**; Radiant Dawn's chapter scripts still call natives its runtime does not model), `colour_variants` and `extended_flags` (the Flags page's Extended storage, **Rename extended...** and **Delete unused**). Screen features say which purpose-built screen a game has so far (`character_form`, `chapter_record_form`, `support_list`, `data_workspace`, `save_units`); a game without one shows its generic record view for the same feature. Table operations the shared pages need (records and their ids, the New record dialog, Excel sheets, terrain names, battle-scenery rows) go through the session's per-game adapter (`fe_modding/game_adapter.py`, `session.adapter`), and Export as text runs the profile's `text_export_parts`. Radiant Dawn's database is `FE10Data.cms`, decoded by `fe_modding/formats/fe10data.py`: the character, class, item and skill tables, whose records are variable-size (a count byte says how many label pointers follow), so an edit that grows or shrinks a record moves every pointer, pointer target and symbol after it. The fixed-size tables are decoded too: chapters, terrain (with its shared stats blocks), supports, army groups, bonds, affinities, affinity pairs, the weapon triangle, the difficulty constants, the battle scenery per map and terrain type and the biorhythm rows; `formats/fe10growth.py` reads `FE10Growth.cms`, the absolute stats of each character at every internal level. Its Game Data page (`Fe10GameDataPage`, the `data_tables` feature) edits all of them in `gui/fe10_data_editor.py`, adds a record as a copy of another and removes one (`fe10data.add_record` / `remove_record`). Its Characters page shares the Path of Radiance card/detail layout and one in-memory data session with Game Data: the character Stats tab groups identity, skills, class-relative stats, animations and Laguz gauge values, Supports edits the affinity/support matrix and bonds, and the other tabs show the portrait, the battle and map models resolved through `FE10Battle.cms` / `FE10Anim.cms` (with **Open in 3D Models** and **Simulate a battle...**), and appearances and script references, which open the character's chapter pages. The project check runs `validator_fe10.py` on Radiant Dawn projects. The disc ID in `sys/boot.bin` (`GFE*` / `RFE*`) identifies the game (`games.detect_from_extracted`); choosing or extracting a disc of the other game warns. The desktop distribution currently targets Windows x64. Portable releases include Python and its dependencies; the first-run setup downloads WIT and optional FFmpeg. See [Windows releases](docs/app/windows-release.md).

Radiant Dawn text (the `dialogue` and `fonts` features, `GameProfile.message_dialect == "fe10"`): the Mess container is Path of Radiance's, but message text is a byte-code instead of `$` commands. `formats/fe10_message.py` tokenizes it losslessly, shows it in a `<...>` notation (`<speaker:04>`, `<show:4D>`, `<w2>`, `<R:上下会話>`, `<FL|PUGO|IKE>`, `<wait>`) and groups it into steps; `message.read_text_order` / `write_messages(..., text_order)` keep a file's text-blob order so an unedited file is rebuilt byte for byte. The Dialogue tab uses `gui/fe10_step_editor.py` and the preview `gui/fe10_conversation_preview.py`, which replays a message per `<wait>` (`formats/fe10_conversation.py`) and draws it (`fe10_conversation_render.py`) from the layout seats and boxes of `window/RectDesc*.bin` (`formats/fe10_rect.py`, including the speech-balloon geometry of the game), the portraits of `Face/facedata.bin` (`formats/fe10_faces.py`), the backgrounds of `s/rect.bin` and the talk font, in 4:3 or 16:9. Radiant Dawn has chapter pages (the `chapters`, `shops`, `play`, `map_decoded` and `battle_sim` features): Overview, Build (canvas, props, terrain, heights, units), Map settings, Chapter data, Dialogue, Script, Shops and Battle scenes all work. `formats/map_file.py` reads both games' `map.bin` through a `MapLayout` picked from the file's own section names: Radiant Dawn prefixes each section with its map folder (`bmap0101:mapdata`), merges `mapcapacity`, `mapextra` and `mapgrid` into one `mapdata` section and widens object (36-byte) and placement (20-byte) records; its `maplight`, `mapfog` and `mapshader` stay raw. Both games edit the story through one interface, `game_code/story_flow.py` (the `chapter_flow` feature, `open_story_flow`): it speaks in chapter-page ids over Path of Radiance's `chapter_flow` table and Radiant Dawn's `rd_story` runtime, so the Overview's next-chapter combo, **Take out of the story**, **Story order...** and **Add chapter...** are the same controls on both games. Path of Radiance's "second part" switch and Radiant Dawn's chapter army (locked until its runtime is checked in game) are per-game fields. Radiant Dawn's **Add chapter...** (`chapters_fe10.py`, through `session.adapter`) gives the copy a custom story number from 56 to 79 and the id `05NN` (56 is `0501`): it copies the map folder, deployments, script and the four message files with their `bmap<id>` names renamed, appends a ChapterData record and a battle-scenery row, copies the shops, and writes the title text and title card. **New campaign...**, hubs (`new_campaign`, `hub`) and map phases (`map_phases`: Radiant Dawn plays a multi-map chapter as consecutive ChapterData records instead) stay Path of Radiance features. Assets › Conversations also opens every Mess file in place. `formats/fe10_conversation_data.py` and Assets › Conversation Lists edit `FE10Conversation.cms` (base Info conversations, found by the symbol `CONV_INFO_DATA_<chapter>_<event>`; the Conversation Room's Path of Radiance supports; support chat lines). The Fonts page lists the profile's `font_files` (eleven LZ10 GCF fonts on Radiant Dawn). `chapters.chapter_titles` reads Radiant Dawn titles from the ChapterData title keys, and the Game Data Chapters tab draws a chapter's `window/title/e_ch<id>.cms` title card (`chapter_images.fe10_title_card`). The engine's name hash has `GameProfile.name_hash_buckets` buckets (509 / 2027), which the Dialogue tab's ID check uses. European text files (`d_ f_ s_ i_`) use single-byte tables that are not decoded yet.

Radiant Dawn graphics use the shared TPL and 3D pipelines. Assets › Portraits reads and writes both FE10 face tables and all LZ10 portrait texture sets, replaces individual pictures with the matching `Face/wide` slot updated by default, edits known placement metadata, and creates removable cloned slots that can be assigned to an FE10Data character; unknown record halfwords remain preserved and read-only. The illustration browser includes FE10's `.cms` artwork. Assets › Icons reads `window/icon.cms`, mirrors replacements into `icon_wide.cms`, labels item and skill cells from FE10Data, and is deep-linked from the RD item and skill forms. Corpus tests cover all 1,054 TPL/CMS files in `Face`, `illust`, `window`, `gmap`, and `etc` on RFEE01. Battle Skies and Battle Scenery Textures additionally expose all 1,350 TPL images embedded in 149 `sky`/`zbg` packs; replacement preserves every non-texture archive member and its metadata. Assets › 3D Models joins RD `pack.cmp` bodies/skeletons with sibling animation-only `.pak` archives and supports view/export, body and animation import, rig replacement and fitting, restoration, and removable cloned `ymu`/`zu` slots; generated archives fully reparse before the write action is offered. The 2,291 RFEE01 archives containing 5,342 `.gs`, 5,342 `.g`, and 16,415 `.ga` components parse and write byte-identically. Assets › Animation Data resolves the 245 model rows into a nine-weapon by 48-motion dispatch matrix with 6,461 active numbered `.ga` variants and safely edits those variant bytes with shared-AID warnings. Assets › Visual Effects decodes the 632-row `FE10Effect.cms` registry, joins it with all 702 `yme` packs, resolves its child effects and 25 numeric-ID aliases, previews their assets, and supports pack/part/texture/particle replacement plus validated registry clone/edit/remove workflows. Assets › Battle Data structurally decodes all 21 fixed-row `FE10Battle.cms` tables, three camera arrays and the shared string pool; it edits relocated names and the five-way map/scenery choices and assigns all 1,112 texture mappings to their unit/model owners. Assets › Battle Cameras correlates the 113 registry names with all 196 loose `xcam` animations, edits weights and the 39-list by 16-context by 30-motion dispatch matrix, imports/replaces/registers clips, and previews them on the shared two-bone rig. `FE10Anim.cms`, `FE10Effect.cms` and `FE10Battle.cms` all have lossless variable-size builders: unchanged RFEE01 files are byte-identical, while structural edits rebuild and validate counts, strings, relocations, symbols and references. Unknown fields remain preserved and read-only.

Radiant Dawn event scripts (the `scripts` feature, `GameProfile.script_dialect == "fe10"`): the `.cmb` layout is Path of Radiance's, and `formats/cmb` handles both bytecodes through a `Dialect` (`model.FE9` / `model.FE10`, read from the compiler build stamp at header +0x18). Radiant Dawn's `localCall` index is one or two bytes, and its compiler emits six more instructions (`inc`, `dec`, `dup`, `ret0`, `ret1`, `assign`); the compiler reproduces its idioms (assignments without `pop`, `return 0/1` as `ret0/ret1`, `ret0` epilogues for callable functions, `switch`/`case` chains, `x++`), so every vanilla script decompiles and compiles back byte for byte. The language gains `switch` and `++`/`--`, which compile only for Radiant Dawn. `catalog.load_externs(dialect)` and `catalog.triggers(dialect)` give each game's natives (`externs_fe10.json`: 656 natives, each described, plus startup.cmb's helpers) and trigger kinds (Radiant Dawn adds rescue, give/take, move-through and epilogue triggers and changes the base-conversation one), and `event_flags.flag_table(dialect)` the flag table (128 slots). Chapter pages open a chapter's script, Assets › Scripts opens every script in the script editor, and Game Data › Flags shows its campaign and chapter flags (a Radiant Dawn save's flags are not decoded yet).

## Chapter data

The **Chapter data** tab is one form on both games (the `chapter_record_form` feature). `chapter_form.py` describes a record's fields once per game, the session's adapter (`session.adapter.chapter_sections`, `chapter_value`, `write_chapter_value`) reads and writes them, and `gui/stats_editor.py`'s `ChapterRecordPanel` and Game Data › Chapters build the same sections from that description: Identity and files, Objectives (text keys), Scenes, then Path of Radiance's Enemy levels and trial grades or Radiant Dawn's Parties (gold account, convoy and the bytes not named yet). Radiant Dawn adds **Title card…** (drawn from the title) and keeps each record's ID and number unique, since the game looks records up by them. **‹ All chapters** opens Game Data › Chapters on the record, on both games.

### Path of Radiance chapter objectives

The form edits the chapter's `FE8Data.bin` record. Its Normal objective slots are:

| Slot | Label | Text key prefix |
| --- | --- | --- |
| 0 | Goal | `MW_` |
| 1 | Goal second line | `MW_` |
| 2 | Defeat condition | `ML_` |
| 3 | Defeat second line | `ML_` |

Hard and Maniac each store three overrides: fields 0, 1 and 2 replace Normal slots 0, 1 and 3. Normal slot 2 is the shared defeat condition. An empty override keeps the Normal text. The music and background fields open their selected cue or resource in Assets › Music or Assets › Backgrounds. Save chapter data with **Save FE8Data.bin**.

## Characters and Game Data on both games

`game_adapter.py` gives each game's session the table operations the shared pages use, so the Characters and Game Data pages hold no game checks:

- **Excel**: `excel_io.export_fe10` / `import_fe10` write one sheet per `FE10Data.cms` table (Characters, Classes, Items, Skills, Terrain) from the table's own field list, label lists as comma-separated text. Each row names its record by `index` and its id; only cells that differ are written, and nothing is written when any row fails. The Characters page and the RD Game Data tables reach them through `session.adapter.export_excel` / `import_excel`, like Path of Radiance's `export_fe8` sheets.
- **Supports tab**: one `gui/support_editor.CharacterSupportsPanel` over `supports_model.py` (`session.adapter.supports_model`). `PorSupports` has C/B/A thresholds, Add/Remove partner, bond effect and value and one conversation button per rank; `RdSupports` edits each character's RelianceData entries (Flag, Speed: every supporter lists all the others, so partners are not added), the KiznaData bond bonus, and opens Assets › Conversation Lists for support talks.
- **Filter chips**: `adapter.categories(kind)`. Radiant Dawn classes are First / Second / Third tier by the tier skills `SID_HIGHER` / `SID_HIGHEST`, and Laguz by the sound class `SFXC_ALIZE`; items go by weapon type.
- **Hub**: both games list the data tiles in the same order. Radiant Dawn's General (Difficulty constants, Army groups) and Supports (Supports, Bonds, Affinities, Affinity pairs) tiles each hold several tables, switched by a strip above the table. Path of Radiance has a Battle scenery tile: the chapter page's Battle scenes panel with a map picker.
- The RD character form has Path of Radiance's **Open** buttons; `character_form.open_map_model` finds an AID's map-model folder through `model_slots.map_model_records` on either game.

Colour variants, the weapon triangle and the biorhythm table are still per game (see `workspace/por-rd-parity-audit.md`).

## Assets on both games

- **Tutorials**: `GameProfile.tutorial_files` names each tutorial list (`tut_data_en.bin`; Radiant Dawn's `Tutorial/tut_data_<n|h>[_en].bin`, the same `formats/tut_data.py` layout), and the editor shows a **List** picker when there are several. `tutorial_flag_names` labels the four start-flag slots (Radiant Dawn's are Slot 1-4 until their difficulties are checked).
- **Battle Weapons**: `battle_weapons_viewer.battle_weapons_panel` picks the page for `GameProfile.battle_dialect`. Path of Radiance edits `xwp/*.dbx` in `zdbx.cmp`; Radiant Dawn edits the `FE10BWeapon` rows of `FE10Battle.cms` (`formats/fe10_battle_weapons.py`: type, model, hit, critical, weapon and target effects) with the same list, form, preview and Restore original. RD rows are edited, not added.
- **Visual Effects**: **Remove added effect** works on both games (`effects.remove_registry_record`). Path of Radiance refuses a record another one chains to, and the game's own records stay protected.
- **Animation Data**: one **Edit…** button. Path of Radiance edits a record's model folder, blend weight and per-army texture numbers (`anim_registry.build_anim_registry`); Radiant Dawn edits a model's variant byte.

## Tools on both games

- **Check**: Radiant Dawn runs Path of Radiance's deployment, script, script-global and shop checks (`validator_fe10.validate_fe10_project` calls the same `validator._check_scripts`, `_check_script_globals` and `_check_shops`). Deployments are the loose `zmap/<folder>/dispos_<diff>.bin` files; every unit's character, class, seven items and five skills must exist, and a label's `/` suffix (`IID_HERB/D`, a dropped item) is a flag, not part of the ID. Both games have a 32-slot script global table (RFEE01 `init_script_tables(0x20, 0x300)`).
- **Export as text**: Radiant Dawn exports deployments, shops and sound as well. Which layout a part reads comes from the profile: a `{diff}` in `GameProfile.deployment` means loose per-difficulty files, `shop_dir`/`shop_file` name the shop files, and a `sound_data` logical file means the cue registry (`sound/bgm_cues.tsv`, `sfx_cues.tsv`) plus the BRSAR's sounds (`brsar_sounds.tsv`).
- **Game Code**: Radiant Dawn's groups carry Path of Radiance's names (Combat rules, Skill activation, Level-up growth, ...) and `CATALOG.groups_for` lists both games' groups in one order. The Skill activation grid is built from `PROC_ROWS` (one tuple per skill in `entries.py` and `entries_fe10.py`) and the Level-up growth grid from the `growth.<mode>.<n>` / `rd.growth.<mode>.<n>` tunables the build has, so Radiant Dawn gets the same grids (random mode only: it has no fixed growth). `RD_GROUP_NOTES` holds the notes whose wording differs.
- **Saves**: Radiant Dawn's save codec reads ITBL, the save's own name tables (`SaveRecord.id_tables`, `id_of`): the Convoy tab names items through it, and shows a forged item's name. Units and flags are not decoded yet (`research/rd/SAVE_NOTES.md`), so the page keeps its Overview, Convoy, Sections and Raw tabs.

None of the parity work has been tried in game yet; [docs/app/parity-test-plan.md](docs/app/parity-test-plan.md) lists the Dolphin checks for both games.

## Chapter dialogue, scenery and forge controls

In Path of Radiance's Dialogue tab, the layout picker shows English names. The editor converts the chosen name back to the game's layout ID when saving; a raw ID can still be entered for an unknown layout. The compact layout and background dropdowns on the two toolbar rows update their matching actions in the message; a missing action is added at the start. **Search…** opens a visual background picker. The step form and preview's initial context offer the same background choices. The Actions menu is one searchable list.

On **Battle scenes**, the first `BattleTerrData` row is a shared fallback. In retail data that row is named `Map6`; this is its stored map name, not a separate mode. A map with no row uses it for every terrain type, and an empty cell in a custom map row inherits that terrain type's entry from the first row. Editing the shared row affects every map that relies on it.

Radiant Dawn's `BattleTerrIndex` works differently (the lookup at `8011d3a4` in RFEE01): a map found in no row fights in front of one fixed backdrop, `bg魔法`, on every terrain type, and row 0 is `bmap00`'s own row. An empty cell uses its row's first cell, so the first cell always needs a backdrop. **Give … its own row** adds a row that starts as `bg魔法` with every other cell empty, so nothing changes until a cell is edited. A backdrop is an `FE10BMapData` record of `FE10Battle.cms`, whose first `FE10BMapModel` names its `zbg/` folder (`bg0101街` is `zbg/bg0101twn`); `RdDataAdapter.scene_models` maps the names, so the scene browser previews them. Thirteen of the 119 backdrops are missing from the retail `BattleTerrName` (`bg汎用02森林` and the other generic ones). Picking one appends it to `BattleTerrName` (`fe10data.add_battle_scenery_name`): the list has no count, the game indexes it directly. A name that is not an `FE10BMapData` record is refused.

On **Shops**, the forge grid has five weapon-family rows and nine fixed base columns. Each cell selects the item offered for that family and base on the selected chapter and difficulty; **(none)** removes that option. Changing a cell does not change the item's stats or price. **Save Shops** writes the selected difficulty's shop file.
